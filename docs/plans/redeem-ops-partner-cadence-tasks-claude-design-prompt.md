# 1. Platform context (ground truth)

## 1.1 The page today

Redeem Ops is an internal partner-CRM at ops.redeem.sg. The **business detail page** (attached screenshot) has:

- A header: avatar, business name, category, phone, website, Instagram handle, pipeline-stage pill (New → Contacted → Meeting → Partnered / Lost), and an action row: Assign to…, Move stage…, Snooze, Release, **Add task**, Log activity.
- A main column with tabs: **Timeline** (activity feed: task created/cancelled, stage moves, claims), Contacts, Locations.
- A **320px right rail** (desktop ≥1024px) with three stacked white cards, `border-radius 16px`, 1px border: **Cadence**, **Owner**, then Notes / Merge / Delete links.
- On mobile, the rail drops below the tabs, so a compact one-line **cadence summary strip** renders directly under the header instead.

## 1.2 The Cadence card today (what you are extending)

- **Enrolled + active:** cadence name + version, an `active`/`paused` state pill, a segmented step-progress bar (done = azure `#037AFF`, current = near-black `#0D1619`, upcoming = light gray), one line "Next: **{task title}** · Wed 15 Jul", and Pause / Stop buttons.
- **Paused:** same, with "Paused — no tasks will be scheduled until resumed." and Resume / Stop.
- **Not enrolled:** "No cadence yet — enroll to auto-schedule every follow-up touch." + a **Start cadence** button (disabled until the business is claimed).
- **Ended:** "Last cadence finished." or "Last cadence ended (reason)." + Start cadence.

## 1.3 Tasks (ground truth data model)

Every task belongs to exactly one business. A task has: `title`, optional `description` (often a call/DM script), optional `snapshotRecipient` (who to contact, e.g. "@codinglabasia" or "+65 9xxx xxxx"), `dueAt`, `status` (`open` | `in_progress` | `completed` | `cancelled`), an assignee (usually the business owner), and **optionally a cadence step** — `{ cadenceName, stepOrder, channel }`.

Two kinds of outstanding task:

1. **Cadence tasks** — generated by the cadence engine, one live task at a time per enrollment. Channel is one of: `call`, `whatsapp`, `email`, `instagram_dm`, `visit`, `custom`. A cadence task is completed **only** through a one-tap **"Outcome"** menu whose options are fixed per channel (this is a hard contract — do not add, rename, or free-text them):
   - call → Connected / No answer / Not interested / They replied
   - whatsapp, email, instagram_dm → Sent / They replied / Not interested
   - visit → Met in person / Outlet closed / Not interested
   - custom → Done / Not interested
   Picking an outcome logs the activity and auto-schedules the next step ("Logged — next step scheduled" toast). **Not interested** first shows a small confirm dialog with an "Also move the business to Lost" checkbox. Tasks with a script/recipient expose a **View script** entry in the same menu (opens the script + "To: {recipient}" in a dialog). Cadence tasks are badged with a zap-icon chip: "⚡ {cadence name} · {step number}".
2. **Manual tasks** — created via the header's **Add task** (title + due date + optional description/assignee). Completed with a plain one-click complete (checkbox/tick); can also be edited or cancelled by whoever manages tasks.

Facts that shape the design: a business can have **several outstanding manual tasks plus at most one live cadence task**; tasks can be **overdue**; the API already lists open + in-progress tasks filtered to one business, so everything you show is real and cheap to fetch.

## 1.4 The problem

Outstanding tasks are invisible on this page. The Cadence card shows only a one-line "Next: …" with **no way to action it**, and manual tasks appear nowhere except the separate Tasks page and as "Task created" entries buried in the timeline. Reps work business-by-business from this page and have to tab away to see or complete what's due.

# 2. The brief

Redesign the **Cadence section of the right rail** so it becomes the single "what's owed on this business" surface: the cadence state **plus an actionable outstanding-tasks list**, together under the Cadence heading as one visual unit. You decide the exact composition — one merged card, or the existing Cadence card with a tasks list under an internal divider — but it must read as one section, sit where the Cadence card sits today, and not balloon the 320px rail (the Owner card stays visible without scrolling on a 900px-tall viewport when ≤3 tasks are outstanding).

Requirements:

1. **Cadence state stays** — name, state pill, step progress, Pause/Resume/Stop — visually tightened if you can.
2. **The live cadence task becomes actionable in place**: title, ⚡ cadence chip, due date, recipient if present, and the **Outcome** menu exactly as contracted in §1.3 (including the Not-interested confirm and View script). This replaces the passive "Next: …" line.
3. **Outstanding manual tasks listed below it**: title, due date, assignee if not the viewer, one-click complete, overflow for edit/cancel. Sorted by due date, overdue first.
4. **Overdue treatment**: unmissable but Fresha-calm — no red flood; think a red-tinted date or a thin left accent, not a filled alert row.
5. **Counts & overflow**: a subtle count in the section header (e.g. "Tasks · 3"). If more than ~4 outstanding tasks, truncate with "View all {n}" linking to the Tasks page pre-filtered to this business.
6. **Add task from here** too (small ghost "+ Add task" at the bottom of the list) — same dialog the header button opens.
7. **Empty/edge states**, all designed: active cadence + no manual tasks; manual tasks + no cadence (Start cadence stays available); nothing at all ("No open tasks — add one or start a cadence"); paused cadence with its task frozen (visually muted, Outcome disabled with a "paused" hint); cadence task overdue; business already Partnered/Lost (no Start cadence, list read-only-ish).
8. **Permissions**: viewers without task-manage rights see the list read-only (no Outcome/complete/add). Assume the viewer is the owner in the default seed.
9. **Mobile**: extend the existing compact summary strip under the header so the due task (and count of remaining tasks) is actionable there too — one row, tap → Outcome menu; don't stack a full card on mobile.
10. **Timeline unchanged** — completions still land there; don't redesign it.

# 3. Design language (already in this project's design system — follow it)

White cards on `#F7F7F8`-ish canvas, 16px radius, 1px `#E5E7EB` border, no shadows heavier than subtle. Ink `#0D1619`, secondary text gray, accent azure `#037AFF` used sparingly (progress, links). Pills/tags are soft-tinted rounded-full with 11–12px semibold text. Buttons: black primary, outlined secondary, ghost tertiary, 8–10px radius. lucide-style 3.5–4px-grid icons. Type scale on the rail: 15px bold card titles, 13–14px body, 11–12px meta. Motion: fast, subtle — menu pops and row-complete fade/strike, nothing bouncy.
